An open PR for the exact pushed implementation branch takes precedence over base integration. The final node verifies the PR head commit and target base (the recorded base when distinct from the head, otherwise an explicit PR target or the verified repository default), returns `mergeStatus: pr-open`, `basePushStatus: not-requested` and the PR identity, and leaves the base untouched. A requested PR with missing, ambiguous, or mismatched evidence blocks instead of merging. Runs without a PR request or open PR retain the existing verified base-integration path.

After accepted implementation review, writable Step 8 owns completed-plan archival, index updates and affected documentation links. Read-only Step 9 verifies those changes and returns exact missing paths to Step 8 when incomplete; it never attempts a filesystem move itself. Intentionally active plans retain their evidence and are not archived merely because a predecessor slice passed. Reviewing the repository `.codex` workflow skill does not require an unrelated edit, and a sandbox-denied required edit is reported honestly.

A failed aggregate is normally a terminal implementation verification blocker. The narrow exception is a completed Step 6 with passing current-source focused tests and retained failed aggregate log plus comparison JSON under task-local `tmp/`; the comparison must prove a positive, exactly matching baseline/current assertion count and no unmatched assertions. A `comparison` path or structured `{path, identical, aggregateAssertionCount, baselineAssertionCount, aggregateOnly, baselineOnly}` record is accepted only when its summary matches the file. A separately reported failed baseline command is supporting evidence only when its log and failure count match that comparison's `baselineLog`; unrelated failures still block. The progress gate returns `baselineReviewPending` and routes to test-integrity, adversarial and integration review without changing either nonzero exit or approving a waiver. Missing/mismatched comparison, new failures, incomplete implementation or absent passing focused evidence still block. Every independent gate must explicitly decide the baseline attribution before publication.

Native join returns branchId/status/sessionId/output, dispatchedBranchIds, pendingBranchIds, completedBranchIds and changeEvidence. Drift is a candidate requiring semantic review. All material integration findings, failed branches and missing worker-owned evidence return to dispatch-plans for selective native Luna redispatch. A blocked-only wave terminates, but a mixed blocked/successful wave carries only evidence-complete candidates through reconciliation and independent integration acceptance; that accepted ID set makes a later dispatch retry only the blocked IDs. Failed branches remain pending and block final completion. Ignore timestamps, generated IDs and artifact paths.

The checkpoint manifest retains all accepted plan references, but plan-checkpoint `committedFiles` contains the manifest and only accepted design/plan paths changed from HEAD. Unchanged accepted paths are excluded so the built-in git commit add-on's exact staged-set check succeeds. The following plan-git-push uses the exact plan-git-commit hash and must succeed before dispatch. Dispatch receives the push receipt in its direct inbox, derives the committed manifest from that exact Git commit, and rejects a missing or unsuccessful push. A no-op checkpoint ends at plan-checkpoint with an explicit blocked payload and never executes plan-git-commit or plan-git-push.

New checkpoints author each plan's `verification` as an array of command strings. Dispatch also projects `verification.commands` from an already committed richer checkpoint object without changing its Git identity; malformed nested evidence requirements and unknown fields remain rejected.

Every dispatched implementation item carries the complete runtime-owned `acceptedPlanIds` set. A worker treats membership in that set as the authoritative predecessor integration decision and must not self-block by reinterpreting older progress or evidence artifacts.

Every implementation and review gate scopes completeness to the current manifest plan. Work explicitly owned by a pending downstream dependent plan does not block, create a finding against, or force speculative repair into its predecessor. Integration review accepts a verified predecessor with `plans_remaining: true`, keeps downstream work pending, and returns the expanded `acceptedPlanIds` that unlock the next native dependency wave. Ambiguous ownership remains a real blocker, and final acceptance still requires every plan and combined behavior.

Planning nodes treat the runner-resolved workflow provenance and effective workflow input as authoritative. They do not rediscover the active workflow through sandbox-local user/project registry commands. Missing sandbox visibility into a user-scope registry or immutable package source is expected isolation and never becomes an intake blocker, design constraint, risk, or plan task. A real provenance, resolution, validation, or package-integrity failure stops the runner before these nodes execute.

Every agent node except `step6-implement` uses Claude Code with `claude-opus-5-5`; design, plan, review and integration-review nodes use high effort and the rest medium. `implementation-wave-outcome` is a deterministic command (`scripts/implementation-wave-outcome.py`), not an agent. `step6-implement` uses Codex `gpt-6-luna` with high effort and the fast service tier (`-c service_tier="fast"`). The implementation fanout transition declares no `concurrency`, so every dependency-ready plan of a wave starts at once.

The design, plan, test-integrity and adversarial review gates are read-only Opus 5.5 reviewers. High/mid findings immediately return to the author (design/plan) or the original GPT-6 Luna step (implementation). Reviewers never edit or delegate repairs. Each finding carries detailed repairRequests and feedback with reproduction, cause, authorized scope, ordered corrections, exact verification and completion criteria. Both implementation review gates run again after Luna corrections. Integration findings redispatch the owning Luna plans with repair_in_place:false. `dispatch-plans` is a deterministic command projection from the direct inbox and exact committed manifest; it does not invoke a model, explore the repository, or recompute native dependency scheduling. It rejects unknown accepted IDs and a dispatch attempt after all plans are accepted.

Integration review stays read-only and returns its immutable wave-acceptance record in the node payload. Runtime session communication persists that accepted output for dependency dispatch; the reviewer is never required to write repository or evidence-root files.

An explicit Step 6 dependency/readiness blocker with no implementation changes bypasses test-integrity and adversarial review. The wave outcome publishes an actionable blocked result before reconciliation, with blocked plan IDs, blockers and resume criteria; it never enters the review/reconcile loop as a successful implementation.

Every branch-local Step 6 result first passes through a deterministic command gate. The gate reads the current and immediately preceding Step 6 payloads from the runtime-owned inbox history, deduplicates and sorts changed files, structured command outcomes and plan updates, and owns the routing discriminator. Explicit blockers, missing evidence arrays, empty progress, non-concrete verification, or evidence that only repeats, reorders or removes immediately preceding items terminate as actionable blocked outcomes before test-integrity. A productive revision with at least one new concrete evidence item continues to test-integrity. Model prose cannot authorize progress, and `implementation_blocked: false` cannot bypass the gate.

Selected Swift-file strict lint requires a nonempty NUL path manifest. The workflow must not invoke SwiftLint with no paths, because SwiftLint then expands repository `included` entries and turns unrelated baseline warnings into false strict errors. An empty selected-Swift set records that no such lint is needed; it is not a passing claim for changed Swift.

The progress gate allows a productive `implementationIncomplete` attempt to return to Step 6 at most twice, but checks material findings and every reported behavioral-test outcome before granting continuation. A high/medium finding (structured severity or an anchored `High:`/`Medium:` self-check line), a failed required test even alongside a passing focused test, or a zero/missing-count test stops with an actionable blocked outcome. Behavioral test records prefer structured nonnegative run/pass/failure counts; a positive run/pass count with zero failures is accepted, while a nonzero or invalid structured failure count is rejected. When no structured positive count exists, anchored legacy summaries `Passed <positive integer> selected tests, 0 failures`, `<positive integer> selected tests passed with 0 failures`, `<positive integer> selected tests, 0 failures`, and `Passed: <positive integer> tests, 0 failures` are accepted. Contradictory structured zero counts, nonzero failures, failed/blocked/skipped outcomes, environmental blockers, and unanchored prose remain rejected. Build, lint, formatting, diff, hash, and documentation commands do not substitute for successful behavioral tests with a positive count. The one exception is a plan whose committed manifest `verification` list contains no behavioral test runner (documentation, packaging, or script-only plans): the gate reads that list from the fanout `implementation` item, requires at least one successful concrete verification record instead of a positive test count, and forwards `verificationPolicy: "plan-declared-static"` so test-integrity and adversarial review still check the declared static commands. When the committed list is missing or empty, the gate fails closed and keeps the behavioral requirement. A pre-compilation environmental failure may reuse the immediately preceding successful behavioral evidence only when both records carry the exact same source identity. When a fresh scratch attempt fails because it cannot fetch dependencies or write module caches, implementation and integrity prompts require retrying the same selected suites against the current tree's already-resolved checkout with plan-local writable caches, no dependency update, complete logs, and positive test count.
